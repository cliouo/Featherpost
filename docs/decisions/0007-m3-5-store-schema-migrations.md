# ADR-0007：M3.5 使用 SQLite user_version 管理 store schema

- 状态：Accepted
- 日期：2026-08-20
- 适用范围：M3.5 store 升级与数据兼容基础

## 背景

此前 `Store::open` 每次直接执行 `CREATE TABLE IF NOT EXISTS`，数据库没有显式版本。这个方式
能创建当前两张表，却无法区分“历史库需要升级”“当前库结构损坏”和“数据库来自更新版本”。
安装器、自动启动和后续升级一旦落地，旧程序误开新 schema 或半完成迁移都可能破坏用户数据。

当前已发布到仓库的历史结构只有 `messages`、两个消息索引和 `otp_notifications`，SQLite
`user_version` 均为 0。因此可以在不改动现有字段和数据的前提下把这份结构登记为 v1。

## 决策

- `SCHEMA_VERSION` 从 1 开始，持久化到 SQLite `PRAGMA user_version`；
- 打开数据库后立即进入一个 `IMMEDIATE` 事务，并在事务内读取版本。若版本高于当前支持值，
  立即 fail-closed；此时不切换 journal mode、不执行 DDL，也不修改版本；
- v0→v1 在同一事务中幂等创建历史表和索引、严格校验字段/主键/必需索引，
  校验通过后才写入 `user_version=1` 并提交；任何一步失败都整体回滚；
- v1 重开不执行迁移，但仍校验两张表的完整字段和必需索引，防止损坏或手工漂移被当作健康库；
- WAL 仍是正常 store 的 journal mode，并只在 schema 事务成功提交后切换。版本读取与写入同处
  一个写事务，避免并发新版本进程在检查后升级、旧进程再把版本覆盖回 v1；
- `StoreOpenError` 区分 SQLite 故障、不支持的未来版本和 schema 不匹配，使插件装配错误能说明
  真实原因。

每次新增 schema 版本都必须提供从上一版本开始的顺序迁移和数据保留测试。不得用“重建空库”
代替迁移，也不得在版本号写入后再执行可能失败的 schema 步骤。

备份/恢复、保留策略、数据库加密和自动降级不属于本决策。它们需要独立的用户动作、原子文件
策略和失败恢复设计，不能隐式夹进 `Store::open`。

## 后果

- 现有 v0 数据库第一次打开会升级为 v1，邮件和 OTP 通知去重标记保持不变；
- 新程序不会打开未来版本数据库，避免旧二进制按旧结构写入；
- 损坏 schema 在启动装配阶段明确失败，不能被错误地提升版本；
- 当前 v1 与历史实际结构相同，因此回滚到本决策之前的代码仍能读取；一旦后续版本改变结构，
  是否允许降级必须由对应 ADR 和迁移单独决定。

## 验证

`tests/store_migrations.rs` 覆盖：

- 新数据库创建为当前版本；
- 含邮件和 OTP 标记的历史 v0 数据库迁移且数据保留；
- 当前版本重复打开幂等；
- 未来版本在 journal mode 和用户数据均不变的情况下被拒绝；
- 损坏的 v0 schema 迁移失败，版本和事务内新建索引一起回滚。
- 损坏的 v1 schema 被拒绝且不会静默修补。
