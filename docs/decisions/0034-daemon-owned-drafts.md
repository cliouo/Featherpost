# ADR-0034：M4.5-G03 daemon 拥有的持久草稿

- 状态：已接受，M4.5-G03 已实现（hermetic e2e 钉死）
- 日期：2026-09-13
- 适用范围：schema v7 → v8（新增 `drafts` 与 `draft_attachments` 两张表）、协议新增
  `listDrafts` / `getDraft` / `createDraft` / `updateDraft` / `deleteDraft` 五个方法与
  `-32005` / `-32006` / `-32007` 三个错误码、授权词表新增 `drafts_read` / `drafts_write`、
  新模块 `drafts`、`maild-client` 类型化 API、`maildctl draft` 子命令
- 关联：ADR-0025（消息模型与正文上限）、ADR-0027（写队列）、ADR-0028（发信组装与
  `prepareReply`，其决策 7 的草稿形状是本片的输入）、ADR-0030（授权词表与两条边界）、
  ADR-0032（daemon 拥有状态的另一种落法，本片刻意作相反选择）、
  [交付计划](../design/tauri/IMPLEMENTATION-PLAN.md) §5 G03 行、[UX-SPEC](../design/tauri/UX-SPEC.md) §6

> 08-A 后续：[ADR-0036](0036-compose-workspace-and-durable-send.md) 已实现原窗口编辑、自动保存与版本化 sendDraft，schema v10 持久化投递状态；本 ADR 的非目标描述对应 G03 当时范围。

> G04 后续：新文件附件现由 [ADR-0035](0035-draft-attachment-staging.md) 实现。schema v9 在草稿附件行持有上传字节；本 ADR 的旧邮件 part 引用、版本化保存与备份语义保留。

## 背景

写信这条路上今天只有两件东西是真的：`prepareReply` 能在内核侧成型一份回复草稿
（ADR-0028 决策 7），`sendFromAccount` 能把字段投递出去。**中间那一段——用户正在写的那封信
存在哪里——不存在。** 旧 egui 桌面把 compose 状态放在进程内存里：窗口一关就没了，进程一崩
就没了。

这个欠账在新形态下比在旧形态下严重得多。ADR-0024 把默认前端定成「按需拉起、随时可关」的
Tauri 窗口，常驻的是 daemon 而不是 UI。**把用户正在写的信放在那个随时会被关掉的进程里，
是把最不该丢的东西放在最容易消失的地方。** 交付计划因此把 G03 的验收写成三句话：

- 输入中崩溃 / 重启，内容可恢复；
- 最后回执之前不得显示「已保存」；
- 过期更新不覆盖。

三句话都指向同一件事：草稿的**属主是 daemon**，前端只是它的一个编辑器。

## 目标

1. 一份草稿在 daemon 侧持久存在：进程崩溃、机器断电、换一个前端打开，内容都还在。
2. 「已保存」有唯一可信来源——一次提交的回执，而不是前端的乐观渲染。
3. 两个编辑者（两个窗口、前端与 CLI、前端与插件）并发写同一份草稿时，**后到的过期写入被拒绝，
   不被静默合并、更不覆盖**。
4. 正文与附件引用归 daemon：转发时引用库内附件不需要把字节搬到前端再搬回来。
5. 不依赖未交付的写信 UI 即可验收（`maildctl draft`）。

## 非目标（明确留给后续切片或明确不做）

- **发送草稿。** `sendDraft` 与发送状态机是 08-A。本片只负责把字段存住、取回，
  它们喂给 `sendFromAccount` 的形状与 `prepareReply` 的输出逐字段对齐。
- **新文件附件。** 从本地磁盘选一个文件加进草稿是 G04（staging 目录、属主与路径硬校验、
  取消与清理）。本片的附件只有一种来源：**库里已有的某封信的某个 part**。
- **同步到服务器的 Drafts 文件夹。** 见决策 8。
- **富文本编辑器与正文的 HTML 生成。** ROADMAP 已列为 M4.5 非目标；`body_html` 由调用方提供，
  内核只负责存取与上限。
- **草稿的自动清理 / 过期。** 用户写了一半的信不该被我们替他删掉。数量上限到顶时拒绝新建
  并说明，而不是淘汰最旧的一份。
- **多设备同步。** 草稿是本机 daemon 的状态。

## 决策

### 1. 草稿是字段，不是报文

`drafts` 行存的是 `from` / `to` / `cc` / `bcc` / `subject` / `body` / `body_html` /
`in_reply_to` / `references` 与一串附件引用，**不存组装好的 RFC 5322 报文**。
组装仍然只发生在发信那一刻（ADR-0028 决策 1）。

两个理由，后一个更硬：

- 每次编辑都要「解析 → 改一个字段 → 重新组装」是把一个简单的行更新做成一次往返的报文
  解析；解析失败还会让用户的文字变成一坨无法编辑的字节。
- **`Date` 与 `Message-ID` 必须在投递那一刻生成**（ADR-0028 决策 4）。把它们烤进草稿，
  意味着一封周一起草、周五发出的信带着周一的日期；而 `Message-ID` 提前生成会让「草稿被
  复制成两封信」变成两封同 ID 的信。字段形态天然没有这个问题。

代价记在这里：草稿里没有「这封信最终长什么样」的权威副本。预览是 08-A 的事，它只能调
组装函数现算。

### 2. 草稿进邮件库（schema v8），与阅读策略作相反的选择

ADR-0032 决策 5 把远程内容策略**故意放在库外的文件里**，理由是「恢复一份旧备份不该悄悄
恢复一份旧的信任名单」——信任是安全状态，回滚它是提权。

草稿的判断正好相反，而且理由是同一套：**草稿是用户写的内容，与邮件同类。**
恢复一份三天前的备份应当把三天前那封没写完的信一起带回来；把它留在库外反而会造成
「邮件回来了、草稿没回来」这种更难解释的半截状态。备份/恢复门禁（ADR-0008/0009）因此
自动覆盖草稿，不需要新的机制。

所以是两张新表，schema v7 → v8：

```sql
CREATE TABLE drafts (
  id TEXT PRIMARY KEY NOT NULL,          -- draft_ + 26 位 base32，与账户/地址行 id 同形
  account TEXT NOT NULL,
  from_address TEXT NOT NULL DEFAULT '', -- 空 = 用账户主地址，发信时解析
  to_addrs TEXT NOT NULL DEFAULT '[]',   -- JSON 数组，逐条原样保存用户输入
  cc_addrs TEXT NOT NULL DEFAULT '[]',
  bcc_addrs TEXT NOT NULL DEFAULT '[]',
  subject TEXT NOT NULL DEFAULT '',
  body TEXT NOT NULL DEFAULT '',
  body_html TEXT NOT NULL DEFAULT '',
  in_reply_to TEXT NOT NULL DEFAULT '',
  reference_ids TEXT NOT NULL DEFAULT '',
  version INTEGER NOT NULL DEFAULT 1,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
CREATE TABLE draft_attachments (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  draft_id TEXT NOT NULL,
  position INTEGER NOT NULL,
  account TEXT NOT NULL,                 -- 源信的账户：跨账户转发是合法的
  folder TEXT NOT NULL,
  uid TEXT NOT NULL,
  part_index INTEGER NOT NULL,
  filename TEXT NOT NULL DEFAULT '',
  mime_type TEXT NOT NULL DEFAULT '',
  size INTEGER NOT NULL DEFAULT 0
);
```

收件人列存 **JSON 数组**而不是逗号连接的字符串：显示名形式（`"Doe, John" <j@d.example>`）
里本来就有逗号，用逗号当分隔符等于给自己埋一个「收件人被劈成两个」的 bug。
`pending_ops.payload` 已经是 TEXT 里放 JSON 的先例。

附件引用存**文件夹名**而不是 `folder_id`：API 与 CLI 讲的是名字，存名字省掉一次翻译；
而文件夹改名会让两种存法同样悬空，代价相等。

### 3. 版本号是唯一的并发仲裁，过期写入一律拒绝

每行有 `version`，创建时为 1，每次成功更新 +1。`updateDraft` 必须带 `base_version`：
与当前值不等就返回 `-32006`（`data.version` 给出当前值），**一个字节都不写**。
`deleteDraft` 的 `base_version` 可选——「丢弃」是用户看着这份草稿做的决定，
但前端仍应带上它，好在别处改过时先问一句。

为什么不是时间戳：两个编辑者可能来自两台机器上的两个进程（前端与 CLI），时钟不可比；
而「谁更晚」本来就不是我们要回答的问题——我们要回答的是「你读到的那份还在不在」。
为什么不做三方合并：邮件正文不是代码，逐行合并出来的东西没人愿意读；把冲突如实报出来、
让用户看着两份内容决定，是唯一诚实的做法。

**这条规则同时定义了「已保存」的唯一含义**：`updateDraft` 的回执携带新的 `version` 与
`updated_at`，那是 SQLite 事务提交之后才产生的。前端在拿到回执之前只能显示「未保存的更改」。
这是交付计划里「最后回执前不得显示已保存」的内核侧对应物。

### 4. `updateDraft` 是 patch，附件整体替换

缺席的字段保持不变；出现的字段整体替换。清空正文是 `"body": ""`，不是省略。
附件出现即替换整张列表（顺序即 `position`），缺席即不动。

patch 而不是全量替换，是因为自动保存会高频发生：一次只改主题不该把 256 KiB 的正文
再搬一遍。安全性由决策 3 兜底——版本号守的是整行，因此**部分字段的更新同样不会丢失
另一个编辑者刚写进去的另一部分字段**：它会先撞上版本冲突。

`setReadingPolicy` 已经是同样的 patch 形状（ADR-0032 决策 5），前端不用学第二套语义。

### 5. 上限一律拒绝，绝不截断

`body` 与 `body_html` 各 256 KiB，主题 2 KiB，单条收件人 320 字节，收件人总数 100
（与 `compose::MAX_RECIPIENTS` 同值），单份草稿附件引用 50 条，单账户草稿 200 份。
超限返回 `-32007`，`data` 指出是哪个字段与上限值。

**截断在这里是不可接受的**：正文是用户刚敲进去的字，悄悄砍掉一半比拒绝保存恶劣得多。
ADR-0025 对收到的邮件正文做截断是另一回事——那份原文在服务器上还有，而草稿没有别的副本。

256 KiB 这个数也不是随手挑的：一次 `updateDraft` 要把 `body` 与 `body_html` 装进同一个
1 MiB 帧（`MAX_FRAME_BYTES`），两个 256 KiB 加上头部与 JSON 转义仍有充裕余量。
`getDraft` 反方向同理。

### 6. 附件是引用，写入时校验，发信时复验

一条附件引用写进草稿之前，daemon 用 G02 的 `Store::read_attachment` 查这个
`(account, folder, uid, part_index)` **真的存在且字节已落库**：不存在返回 `-32003`，
只有元数据没有字节返回 `-32004`。这两个码与 `readAttachment` 同义，前端不用学新的。

写入时校验不是保证：源邮件可能在草稿写完之后被删掉。所以 08-A 发信时必须**再查一次**，
失败时告诉用户是哪一个附件没了——而不是发出一封少了附件的信。本片把这条写成契约，
并在 `getDraft` 的回执里带上每条引用的当前 `stored` 位，让 UI 能提前把话说在前面。

`filename` / `mime_type` / `size` 是写入时的快照，只为显示；它们与源 part 的差异
不影响发信（发信读的是引用，不是快照）。

### 7. 两个新授权词：`drafts_read` 与 `drafts_write`

草稿**不并进 `messages_read`**。理由是这两类内容的性质不同：收件箱里的信是已经送达的
既成事实，而草稿是用户还没决定要不要发的字。一个只申请了「读邮件」的插件，没有理由
自动获得「看用户正在写什么」的能力。

也**不并进 `messages_send`**。反方向的论证同样成立：一个能改草稿的主体，可以在用户按下
发送之前换掉收件人；而一个能发信的主体，并没有理由能翻用户的草稿箱。两者谁也不包含谁。

拆成读写两个词而不是一个 `drafts_manage`，是照 `settings_read` / `settings_write` 的既有
形状办事，而且这两侧都有真实的单边用例：一个「草稿数量」的侧栏小挂件只要读；
一个「把模板插成一份草稿」的插件只要写；而「AI 起草回复、用户审阅后自己发送」——
这正是项目愿景里插件系统要覆盖的那类定制——要读写但**恰恰不该要 `messages_send`**。

两个词在 frontend 与 external 两张词表里都可声明。三个管理词（`accounts_manage` /
`addresses_manage` / `plugins_manage`）是 frontend-only，因为后台插件没有理由改账户配置；
草稿不属于那一类，一个后台插件为用户起草一封信是正当用途。

路由与授权是两个字段（ADR-0030 决策 2）：声明 `compose` 路由只说明「写信这个 intent 交给我」，
它**不隐含** `drafts_write`。想存草稿的前端必须自己写出来。

默认前端 `com.maild.ui` 的 manifest **本片不加这两个词**——它现在还没有写信 UI，
声明用不到的权限与 ADR-0030 决策 9「内置前端不做例外」相悖。08-A 落地时再加。

### 8. 不同步到服务器的 Drafts 文件夹

草稿只存在于本机 daemon。不 `APPEND` 到 IMAP 的 Drafts。

这不是偷懒，是因为**「同步草稿」和「存草稿」是两个不同的功能，混在一起两个都做不好**：

- IMAP 没有「更新一封信」这个操作。每次自动保存都得 `APPEND` 一份新的再把旧的 `\Deleted`
  + `EXPUNGE`，一次击键风暴会在服务器上留下一串墓碑；
- 那条路必须经过写队列（ADR-0027），于是「保存成功」就变成异步的，
  与决策 3 的「回执即已保存」直接冲突；
- 存回去的是组装好的报文，读回来要重新解析成字段——决策 1 拒绝的正是这件事，
  而跨端往返会让它必然发生一次。

诚实的后果：在手机上看不到电脑上写了一半的信。这是本片明确的边界，不是 bug。
真要做的话正确形状是「本地草稿为真值，向 Drafts 单向发布一个只读快照」，那是独立切片。

### 9. 不推送草稿事件

不新增服务端通知。推送流的授权词是 `messages_read`（api.rs 的 `EVENT_CAPABILITY`），
把草稿内容推给每一个持 `messages_read` 的主体，正好把决策 7 刚划下的界又抹掉。

跨窗口一致性由版本冲突兜底：第二个窗口的过期保存会被拒绝并看到当前版本号，
而不是悄悄覆盖。这已经是「不丢内容」所需要的全部。真需要实时联动时（E03 的可分离窗口），
再加一个以 `drafts_read` 为授权词的定向事件，那时它有明确的消费者。

### 10. `maildctl draft` 让 G03 不依赖 UI 即可验收

`draft list` / `show` / `new` / `set` / `attach` / `detach` / `rm`。
`--body-file -` 从 stdin 读正文——这同时是「大正文不经 shell 参数」的正路。
`set` 与 `rm` 都要 `--version`，CLI 因此也是版本冲突这条规则的第一个真实使用者：
在没有任何 UI 的情况下，两个终端就能把「过期更新不覆盖」演一遍。

## 备选方案与取舍

| 方案 | 为何不选 |
|---|---|
| 草稿留在前端进程内存里（现状） | 按需拉起的窗口随时会关；把最不该丢的东西放在最容易消失的地方 |
| 草稿存在前端自己的存储里（localStorage / 前端配置文件） | 换一个前端就换一套草稿；且 webview 侧存储不在备份门禁内 |
| 草稿存成库外的 JSON 文件（照 ADR-0032 的阅读策略） | 草稿是用户内容，应当随备份恢复一起回来；而且它需要事务化的版本推进 |
| 存组装好的 RFC 5322 报文 | 每次编辑要解析再组装；`Date` / `Message-ID` 会被提前烤死（ADR-0028 决策 4） |
| 用 `updated_at` 时间戳做并发仲裁 | 两个编辑者的时钟不可比；要回答的本来就不是「谁更晚」而是「你读到的那份还在不在」 |
| 冲突时做三方合并 | 正文不是代码，自动合出来的段落没人愿意读 |
| 冲突时后写者胜 | 这就是「过期更新覆盖」本身，交付计划点名要避免的 |
| `updateDraft` 全量替换 | 自动保存高频发生，只改主题不该重传 256 KiB 正文 |
| 超限时截断正文 | 草稿没有第二份副本；悄悄砍掉用户刚敲的字比拒绝保存恶劣得多 |
| 草稿数到顶时淘汰最旧的 | 用户写了一半的信不该被我们替他删掉 |
| 附件引用存字节的副本 | 库里已经有一份；复制一份等着与源 part 不一致 |
| 草稿并进 `messages_read` | 只申请读邮件的插件会自动获得「看用户正在写什么」 |
| 草稿并进 `messages_send` | 能发信不等于该翻草稿箱；两者谁也不包含谁 |
| 一个 `drafts_manage` 覆盖读写 | 读写两侧都有真实单边用例；`settings_read`/`settings_write` 已是同形先例 |
| 同步到 IMAP Drafts | IMAP 没有「更新一封信」；每次自动保存留一串墓碑，且保存变异步，与「回执即已保存」冲突 |
| 新增草稿推送事件 | 推送流的授权词是 `messages_read`，会把决策 7 刚划的界抹掉 |

## 兼容性

- 协议 additive：五个新方法、三个新错误码，既有方法的参数与应答逐字节不变。
- 授权 additive：两个新词；不声明它们的既有前端/插件行为不变，调用新方法被 `-32016` 拒绝。
  **旧 daemon 遇到声明了新词的 manifest 会整份拒绝**（枚举是 `deny_unknown_fields` 的），
  这是既有的 fail-closed 行为，不是本片引入的。
- schema v7 → v8 是纯新增两张表，既有表一列不动。`maild backup` / `restore` 自动覆盖。
- **回滚到 v8 之前的二进制无法打开已升级的库**，与既往每次升版一致；
  草稿会随备份一起被带回旧版本无法理解的状态，因此降级路径仍然是「恢复升级前的备份」。

## 测试策略（hermetic）

`crates/maild/tests/drafts.rs` 与模块单测覆盖：

- v7 → v8 迁移：既有数据无损、新表结构逐列校验、v1–v7 备份恢复路径照旧；
- 创建 → 更新 → 读回：字段逐一相等，`version` 单调递增；
- **过期更新不覆盖**：以 `base_version = 1` 连发两次，第二次得 `-32006` 且内容仍是第一次的；
- **重启恢复**：写入后关掉 daemon、重开库，内容与版本号都还在；
- 保存失败不损坏既有版本：超限的 `updateDraft` 返回 `-32007` 之后，`getDraft` 仍是旧版本；
- 上限逐项：正文、主题、收件人条数与长度、附件条数、单账户草稿数；
- 附件引用：四元组任一元不匹配 → `-32003`；元数据在但字节未落库 → `-32004`；
  跨账户转发的引用可写入并原样读回；
- 授权：只声明 `drafts_read` 的主体读得到、写被 `-32016` 拒绝；两个词都不声明的主体两边都被拒；
- 控制字符：`To` / `Subject` 里的 CR/LF 在写入时就被拒（头注入的最早一道门）；
- 假 daemon e2e：`maildctl draft` 全链跑通，两个并发 `set` 演出版本冲突。

## 后果

- 写信这条路上第一次有了「内容不会丢」这个性质，且它不依赖任何前端还活着。
- 「已保存」从此是一个有明确来源的事实，前端不能自己发明它。
- 授权词表从 11 个变成 13 个。每多一个词，manifest 审阅就多一行要看——这是为
  「AI 起草但不能发信」这类插件付的价，值得，但不是免费的。
- 草稿只在本机：换台设备看不到写了一半的信。
- 草稿参与备份与恢复，因此**一份旧备份会把旧草稿带回来**，包括用户以为已经删掉的那份。
  这与邮件的行为一致，但与阅读策略（ADR-0032 决策 5 刻意不进库）相反，
  两处的理由都写在各自的 ADR 里。
- 08-A 拿到的是一个已经可用的草稿后端，它要做的只剩编辑器、自动保存节流与发送状态机。
