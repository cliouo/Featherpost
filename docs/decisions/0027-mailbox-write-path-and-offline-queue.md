# ADR-0027：M4.5-05 邮箱写路径与离线队列

- 状态：已接受（2026-08-29）
- 关联：ADR-0007（迁移框架）、ADR-0018（方法授权表）、ADR-0025（消息模型）、
  ADR-0026（文件夹与增量同步）；ROADMAP M4.5-05

## 背景

到 M4.5-02 为止，maild 对服务器**只读**。已读、星标、归档、删除——一个邮箱客户端每天用得最多的
四个动作——一个都做不到。`messages` 表里的 `seen`/`flagged`/`answered`/`deleted` 四个标记位自
ADR-0025 起就存在，但它们只是「上次抓到时的快照」，没有任何回写路径。

写路径的难点不在 IMAP 命令，而在**失败语义**。网络会断，而 IMAP 没有幂等键：

- `UID STORE +FLAGS (\Seen)` 重放是安全的（置位两次和一次一样）；
- `UID MOVE` 重放**不安全**（会在目标文件夹产生第二份副本）。

于是「命令已发出，但没看到 tagged 响应」这个状态对后者既不是成功也不是失败。绝大多数客户端把它
折叠进「失败」然后自动重试，代价是偶尔冒出重复邮件——用户看得见，却无从解释。

## 目标

1. 已读/星标/已回复的置位与取消、归档（移动）、删除可用，且**点了立刻生效**，不等网络。
2. 离线时排队，恢复连接后按序执行；执行结果对用户可见、可裁决。
3. 「结果未知」是一个独立的终态，不被伪装成失败。
4. 重连后与服务器对账标记位，但**不覆盖**用户刚做的本地改动。
5. 协议 additive，代数不提升。

## 非目标

- **`APPEND` 与草稿保存**：归 M4.5-06（发信补全）。
- **撤销（undo）**：需要反向 op、时间窗口与前端交互，归前端切片。
- **彻底删除（purge）**：废纸篓里的二次删除需要不可撤销确认，且没有回头路，单独设计。
- **文件夹的创建/重命名/删除**：ADR-0026 已声明只读同步。
- **服务器端 `EXPUNGE`/`VANISHED` 未推送消费**：本片以对账的方式发现消息消失（决策 6），
  不订阅实时通知。

## 决策

### 1. 本地乐观写与入队在同一个事务里

用户点「已读」，列表必须立刻变。所以本地状态改写与 `pending_ops` 入队在同一个 IMMEDIATE
事务内提交——不存在「本地改了但队列没入」或者反过来的中间态。这是整条写路径的地基：
本地状态与待办队列永远一致，崩溃后重放也一致。

### 2. 三个终态，「结果未知」是其中之一

```
pending ──claim──> in_flight ──┬── done      服务器返回 OK
                               ├── failed    服务器明确拒绝（NO / BAD）
                               └── unknown   命令已发出，未见 tagged 响应
```

`unknown` **不是** `failed` 的一种：

- 对**可重放**的操作（flag 类）`unknown` 可以自动重试——`STORE` 幂等，最坏是多设一次同样的位。
- 对**不可重放**的操作（move / delete）`unknown` 是**终态**，不自动重试。重放会在目标文件夹
  产生第二份副本，而我们无从判断第一次到底成没成。这时把事实原样交给用户：
  「这封信的归档结果未知，请检查目标文件夹」，由用户选择重试或放弃。

这是本片最重要的语义。把它折叠掉能省一个状态和一段 UI，代价是偶发的重复邮件——那是用户看得见
却无从解释的损坏，比多一个状态贵得多。

### 3. `MOVE` 的降级链；没有 UIDPLUS 就不 `EXPUNGE`

- 服务器宣告 `MOVE`（RFC 6851）→ `UID MOVE`，原子，一条命令。
- 否则 `UID COPY` + `UID STORE +FLAGS (\Deleted)`。
- 之后是否 `EXPUNGE`：**只有宣告 `UIDPLUS`（RFC 4315）时**才发 `UID EXPUNGE <uid>`。

没有 UIDPLUS 就不 `EXPUNGE`。裸 `EXPUNGE` 作用于整个 mailbox，会连带清除**其他客户端**标记了
`\Deleted` 的邮件——那是别人的数据，我们没有权限替它做决定。此时源邮件留在原文件夹并带
`\Deleted` 标记，这正是 RFC 3501 的删除模型，也是经典 IMAP 客户端几十年的行为。

### 4. 删除 = 移进废纸篓；没有废纸篓才落 `\Deleted`

`deleteMessages` 不是「立刻抹掉」：

- 账户有 `role = trash` 的文件夹且消息当前不在其中 → 按决策 3 移过去；
- 消息已经在废纸篓里，或该账户根本没有废纸篓 → `+FLAGS (\Deleted)`（EXPUNGE 仍按决策 3）。

这条策略在**内核侧**判定，不在前端。换前端不会换掉删除语义。

判定发生在**入队时**而不是执行时：`deleteMessages` 据此入队一个 `move`（到废纸篓）或一个
`flag`（`\Deleted`）。因此队列里只有两种 op，且每一条的可重放性在入队那一刻就已确定
（决策 2 依赖这一点）。代价是入队后废纸篓才被 `LIST` 发现的话，这一批会走 `\Deleted` 路径。

### 5. 乐观移动的本地表现是「从源文件夹消失」

`UID MOVE` 成功后，这封信在目标文件夹里有一个**全新的 UID**，本地无从预知（`COPYUID` 需要
UIDPLUS，且客户端库未暴露）。所以移动的本地效果不是「改 `folder_id`」，而是：

- 立刻把源行标记为 `pending_removal`，列表与计数不再包含它——用户看到的就是「它走了」；
- op `done` → 删除源行。目标文件夹在下一次同步时把它作为新消息抓回来（若目标是主文件夹则几乎立刻）；
- op `failed` → 清除标记，消息**回到**源文件夹；
- op `unknown` → 保持隐藏，并在 `listPendingOps` 里等用户裁决。用户选「放弃」则清除标记，
  由决策 6 的存在性对账收敛真相。

代价诚实写在这里：移动后的消息会在目标文件夹「迟到」最多一个 `folder_poll_secs`。

### 6. 对账跳过最近的本地改动；存在性对账是全量 FETCH 的副产品

重连后拉一次 `UID FETCH <range> (UID FLAGS)` 与服务器对账。两条护栏缺一不可：

分类的入口不止是命令本身：执行前的 `SELECT` 同样按这条规则分类。服务器明确拒绝
（文件夹已经不在了）意味着命令**根本没发出**——那是 `failed`，消息回到源文件夹，
而不是把它挂在「结果未知」上等用户裁决一件从未发生的事。

进程崩溃时停在 `in_flight` 的 op 与失联是同一种处境：下次连接建立时统一收敛——可重放的回到
`pending`，不可重放的落到 `unknown`。

- **时间窗口**：`messages.flags_local_at` 记录最后一次本地乐观改写的时刻，对账跳过
  `flags_local_at` 在最近 `RECONCILE_SKIP_SECS`（60 秒）内的行。挡的是「op 刚 done、
  服务器的这次 FETCH 还没反映出来」的竞态。
- **未完成队列**：任何还有未完成 `pending_ops` 的 `(folder, uid)` 一律跳过。挡的是长时间
  离线后堆积的写——它们可能已经排了几小时，早就落在时间窗口之外。

只有当这次是**全量**对账（没有用 `CHANGEDSINCE` 截断）时，才顺带做存在性对账：本地有、
服务器返回的 UID 集合里没有的行，说明已被其他客户端 `EXPUNGE`，本地删除。这近乎免费——
同一次 FETCH 已经把全部 UID 拿回来了。两条跳过护栏同样适用；只在响应流**完整读完**后才动手。

### 7. `CONDSTORE` 短路整段对账

服务器宣告 `CONDSTORE`（RFC 4551）时用 `SELECT ... (CONDSTORE)` 取 `HIGHESTMODSEQ`：

- 与库内记录一致 → 该文件夹自上次同步以来**没有任何标记变化**，整段对账跳过；
- 不一致 → `UID FETCH <range> (UID FLAGS) (CHANGEDSINCE <modseq>)`，只拉变化的部分。

不支持 CONDSTORE 时退回全量对账，并且**只在连接建立时做一次**，不挂在 IDLE 唤醒的热路径上——
对账是 O(mailbox)，每来一封新信就重跑一遍是不可接受的。

### 8. 写路径复用收信那条连接

ADR-0026 决策 3 定下每账户恒一条 IMAP 连接。写路径不另开连接：API handler 只做「本地改写 +
入队 + 唤醒」，命令的实际执行发生在收信循环里，在 IDLE 之间的间隙。

好处不只是省一条连接：读与写因此天然串行，IMAP 会话状态（当前选中的 mailbox）不需要任何并发
保护。执行器为一批 op 切换到目标文件夹，做完再回主文件夹。

代价是账户离线时写会排队而不是立刻失败——这正是「离线队列」要的行为。

### 9. 写方法是 `UserOnly`

与账户域（ADR-0015）和地址域（ADR-0022）一致，`markMessages` / `moveMessages` /
`deleteMessages` / `listPendingOps` / `resolvePendingOp` 全部登记为 `UserOnly`。

并进 `messages_read` 会让任何可读插件删除用户的邮件；并进 `messages_send` 也不对——那是投递域，
不是信箱状态域。将来外部前端确实需要写权限时，那是一次**刻意的** capability 词表扩展
（ADR-0014 §5 的 manifest 与 ADR-0018 的路由翻译表都要动），不能顺手授予。

内置桌面与 ADR-0024 的默认 Tauri 前端都以 user 主体连接本地 socket，不受影响。

> **2026-09-11 更新（[ADR-0030](0030-frontend-authorization-closure.md) 决策 4/5）**：上一段
> 预告的那次「刻意的词表扩展」已经发生。五个方法改归新词 `mailbox_write`，manifest 侧不是扩路由
> 翻译表，而是把路由与授权拆成两个字段——挂到 `message` 路由上会给已安装的只读前端静默提权。
> 本节的判断因此原样成立，变的只是它现在有了自己的名字。该词同时进入 external 词表：自动归档
> 的规则插件需要它，而且必须显式声明。最后一段也已修正——核验发现内置 egui 壳确实以 user 运行，
> 但 Tauri 前端将以 `frontend:com.maild.ui` 认证，正是为了让扩展代理层有一个不靠自觉的天花板。

### 10. schema v4 → v5

- 新表 `pending_ops(id, account, folder_id, uid, kind, payload, state, attempts,
  created_at, updated_at, detail)` + 按 `(account, state, id)` 与 `(account, folder_id, uid)` 的索引。
  `kind` 只有 `flag` 与 `move` 两种（决策 4）；`payload` 是 JSON，flag 类带 `previous`
  以便失败时把本地状态还原成用户点击之前的样子；
- `messages` 增 `flags_local_at INTEGER`（决策 6）与
  `pending_removal INTEGER NOT NULL DEFAULT 0`（决策 5）；
- `folders` 增 `highest_modseq INTEGER`（决策 7）。

`kind` 与 `state` 都带 `CHECK` 约束，读取侧对未知取值 fail-closed——沿用 ADR-0022 地址层的纪律：
一个未来版本写入的状态值绝不能被当成 `pending` 重新执行。

## 备选方案与取舍

| 方案 | 为何不选 |
|---|---|
| 「结果未知」折叠进 failed 并自动重试 | `MOVE` 不幂等，重放会产生重复邮件——用户看得见却无从解释 |
| 「结果未知」折叠进 done | 反过来会静默丢失用户的操作 |
| 全部 op 都自动重试，靠 `Message-ID` 事后去重 | `Message-ID` 不保证唯一（ADR-0026 决策 1 已论证），去重会误删 |
| 写路径另开一条 IMAP 连接 | 与 ADR-0026 的连接预算冲突；且读写并发会引入 mailbox 选中状态的竞态 |
| 不做乐观写，等服务器确认再改本地 | 每次点击都要等一个 RTT，离线时完全不可用 |
| 对账无条件以服务器为准 | 会把用户刚点的「已读」弹回去——最典型的同步类 bug |
| 只用时间窗口保护乐观写 | 离线堆积的写早就落在窗口之外；必须同时看未完成队列 |
| 只用未完成队列保护 | op 刚 done 但服务器的这次 FETCH 还没反映出来，仍会被弹回 |
| 每次 IDLE 唤醒都对账 | 对账是 O(mailbox)，每来一封信重跑一遍不可接受 |
| 无 UIDPLUS 时也 `EXPUNGE` | 裸 `EXPUNGE` 会清除其他客户端标记 `\Deleted` 的邮件——那是别人的数据 |
| `deleteMessages` 直接 `\Deleted` + `EXPUNGE` | 用户对「删除」的预期是可找回；有废纸篓就该用废纸篓 |
| 移动时本地直接改 `folder_id` | 目标文件夹的 UID 由服务器分配，本地无从预知；伪造一个 UID 会与真实同步冲突 |
| 写方法归 `messages_read` | 任何可读插件都能删用户的邮件 |

## 后果

- 账户离线时写入不报错而是排队。UI 必须能显示队列深度，否则用户会以为操作丢了。
- 移动后的消息在目标文件夹最多迟到一个 `folder_poll_secs`（默认 300 秒）。
- 不支持 UIDPLUS 的服务器上，「删除」在没有废纸篓时表现为「标记为已删除但仍在列表里」。
  这是 RFC 3501 的模型，不是缺陷，但需要在 UI 上说清楚。
- 存在性对账使「在手机上删掉，桌面也消失」成立，但只在**全量对账**的那一次；
  用了 `CHANGEDSINCE` 截断的轮次不做存在性判断（拿不到完整 UID 集合）。
- 回滚到 v5 之前的二进制无法打开已升级的库（ADR-0007 fail-closed）。
- 已入队但未执行的 op 在降级后不会被旧版本消费，也不会丢失——它们留在表里。

## 验证

`crates/maild/tests/` 覆盖：

- v4 → v5 迁移与 v1–v4 备份恢复路径；畸形 v4 结构 fail-closed 且整体回滚；
- 乐观写与入队的原子性：本地状态与队列同进同出；未知 `state`/`kind` 读取 fail-closed；
- 状态机：`pending → in_flight → done/failed/unknown`；flag 类 `unknown` 自动重试，
  move 类 `unknown` 是终态且不自动重试；`resolvePendingOp` 的 retry 与 discard；
- 对账：服务器与本地不一致时以服务器为准；**但**最近本地改动与有未完成 op 的行不被覆盖；
- 存在性对账：全量轮次删除服务器上已消失的行，`CHANGEDSINCE` 轮次不删；
- `CONDSTORE`：`HIGHESTMODSEQ` 未变时整段跳过；
- 假服务器 e2e：标记回写后重连仍为已读；移动后源文件夹不再包含它；
  `MOVE` 不可用时降级 `COPY` + `\Deleted`，无 UIDPLUS 时不发 `EXPUNGE`；
- 协议：五个方法归 `UserOnly`（ADR-0030 起改为 `mailbox_write`），未授权主体一律 `-32016`；参数校验；additive 回归。
