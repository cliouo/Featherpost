# ADR-0028：M4.5-06 发信补全、回复/转发与 Sent 归档

- 状态：已接受（2026-08-29）
- 关联：ADR-0021（委托发信）、ADR-0022（别名发信）、ADR-0025（消息模型）、
  ADR-0026（文件夹）、ADR-0027（写队列）；ROADMAP M4.5-06

> 后续 G04 已由 [ADR-0035](0035-draft-attachment-staging.md) 补齐新文件附件上传：保存到草稿后按 `{draft_id, upload_id}` 发送，额外要求 `drafts_read`；原有 MIME/SMTP/Sent 流程保留。文件名参数升级为 RFC 2231。

## 背景

发信路径自 R4 起就没动过：`send(from, to, subject, body)` 拼三个头、一个纯文本正文、
一个收件人，然后 `DATA`。作为演示够用，作为邮箱客户端缺得很彻底：

- **没有 Cc / Bcc**，只能发给一个人；
- **没有 `In-Reply-To` / `References`**，回复挂不到会话上——M4.5-01 已经把这两个头存进库里了，
  但发信侧从来不用；
- **没有 `Date` 与 `Message-ID`**，靠服务器补。补出来的 `Message-ID` 我们不知道，
  于是本地永远无法把「我发出去的那封」与会话对上；
- **非 ASCII 头部直接塞 8bit**，中文主题在不少服务器上会被拒或乱码；
- **没有 HTML 正文**，也没有附件；
- **发出去的信不进已发送**：SMTP 投递与 IMAP 信箱是两条独立通道，不 `APPEND` 就没有存档
  （部分服务商会替你做，但不能指望）；
- **没有回复/转发**：头继承、引用正文、`Re:`/`Fwd:` 归一全都不存在。

## 目标

1. 一封发出去的信在 RFC 5322 意义上是完整的：日期、Message-ID、正确编码的头部与正文。
2. Cc / Bcc / 多收件人；Bcc 只进信封。
3. 回复、全部回复、转发在**内核侧**成型，前端只负责编辑与提交。
4. 投递成功后归档到已发送，且归档失败不影响「已经发出去」这个事实。
5. 协议 additive，代数不提升；别名发信（ADR-0022）语义不变。

## 非目标

- **新文件附件上传**：见决策 8 的诚实边界。
- **草稿保存**：`APPEND` 到 Drafts 用的是同一套机制，但草稿还需要生命周期（编辑替换、删除、
  与本地编辑器状态的一致性），单独设计。
- **富文本编辑器**：ROADMAP 已列为 M4.5 非目标；HTML 正文由调用方提供。
- **DSN / 已读回执 / PGP / S-MIME**。
- **头部与引用文案的多语言**：见决策 7 的诚实边界。

## 决策

### 1. MIME 组装在内核，不在前端

`compose` 模块负责头部编码、multipart 结构、引用正文与主题归一；前端拿到的是一份**草稿**，
提交的是字段而不是拼好的报文。

理由与 ADR-0024 的取舍一致：换前端不该换掉 `References` 的正确性。让三个前端各写一遍
引用格式、`Re:` 归一和 encoded-word，只会得到三种互不相同的错。

### 2. Bcc 只进信封，绝不进头

`RCPT TO` 包含 to + cc + bcc 的并集，但 `DATA` 的头部只写 `To:` 与 `Cc:`。

这不是实现细节而是安全属性：bcc 出现在头里等于把密送名单直接发给所有收件人。
现有的头注入防线（`validate_send_field` 对 From/To 只接受单个 ASCII addr-spec，
因此 CR/LF 根本无法通过）**逐项**扩展到 cc 与 bcc 的每一个元素——校验的是每个地址，
不是拼接后的字符串。

### 3. 收件人字段接受字符串或数组

`to` / `cc` / `bcc` 都接受「单个字符串」或「字符串数组」，前者等价于单项数组。
这样旧客户端的 `to: "a@b"` 逐字节不变，新客户端可以传数组。收件人总数有上限（100），
避免一次请求变成群发工具。

### 4. `Date` 与 `Message-ID` 由我们生成

RFC 5322 要求 `Date`，并 SHOULD 要求 `Message-ID`。自己生成的直接好处是**本地知道这封信的
`Message-ID`**——`APPEND` 到已发送的副本与投递出去的那封是同一个 ID，会话链因此闭合。

- `Date`：外发报文头采用 RFC 5322 格式，恒用 `+0000`（UTC），不引入外部日期库，用 civil-from-days 换算。固定 `+0000` 的理由是**发件人物理时区隐私**（不向收件人暴露本机 UTC 偏移与差旅行踪）以及 **Sent `APPEND` 与持久写队列载荷的确定性**；而 `prepareReply` 生成的回复/转发引用行面向本机作者阅读，按回复者的系统本地时间并附显式偏移（如 `2026年11月18日 周三 19:35（UTC+08:00）`）格式化（不可拆解时回退 RFC 5322 `+0000`）。
- `Message-ID`：`<`+ 密码学 RNG 的 base32 + `.` + 时间戳 + `@` + From 的域名 + `>`。

### 5. 非 ASCII 头部走 RFC 2047 encoded-word

主题与显示名可能是中文。按 RFC 2047 编成 `=?UTF-8?B?...?=`，并按 75 字符行限分段折行；
每段在 UTF-8 字符边界切分，绝不切出半个字。纯 ASCII 且无特殊字符的头部原样输出——
不给英文邮件平白加一层编码。

### 6. 正文编码只在 `7bit` 与 `base64` 之间选

正文是纯 ASCII 且行长安全（≤ 998 字节）时用 `7bit`，原样可读；否则整体 `base64`。

不实现 quoted-printable：它对中文的膨胀率是 3 倍（base64 是 4/3），而它唯一的优势——
「原始报文里英文仍可读」——只在混合内容里成立。少一个编码器就少一处会出错的地方。

这条选择还有一个副作用值得记下来：**组装完的报文一定是纯 ASCII**。因此它可以原样放进
`pending_ops.payload` 这个 TEXT 列（决策 9），不需要额外的二进制通道。

### 7. 回复 / 全部回复 / 转发在内核成型

`prepareReply { account, folder, uid, mode }` 返回一份草稿：

| mode | `to` | `cc` | 主题 | 正文 |
|---|---|---|---|---|
| `reply` | `Reply-To` ?? `From` | 空 | `Re: ` + 归一后的主题 | 引用块 |
| `reply_all` | `Reply-To` ?? `From` | 原 `To` ∪ `Cc` 去掉自己 | 同上 | 引用块 |
| `forward` | 空 | 空 | `Fwd: ` + 归一后的主题 | 转发块 + 原附件 |

- **主题归一**：反复剥掉开头的 `Re:` / `RE:` / `答复:` / `Fwd:` / `FW:` / `转发:` 再加一个前缀，
  避免 `Re: Re: Re:` 累积。
- **`References` 继承**：原信的 `References` 追加原信的 `Message-ID`；原信没有 `References`
  时退回 `In-Reply-To`。总长有上限，超限时保留**首条与最后若干条**——首条是会话根，
  丢了会话就断，这一点比丢中间几条严重得多。
- **「自己」的判定**：账户 profile 地址加上该账户在地址层（ADR-0022）里的全部别名。
  全部回复不该把信抄送给自己。
- **转发携带原附件**：附件字节已经在库里（ADR-0025），按 `(folder, uid, part_index)` 引用即可，
  不需要任何上传。

诚实边界：引用块的文案（「在 …，… 写道：」）目前只有中文。maild 还没有 i18n 框架，
与其发明一个不如把这件事记在这里——它是一个独立的小切片，不该混在发信里做。

### 8. 新文件附件不在本片

转发能带上原附件（决策 7），但「选一个本地文件发出去」不行。原因是**协议单帧上限 1 MiB**：
base64 之后能塞进去的实际文件不到 700 KiB，任何一张手机照片都超。做一个用起来就失败的功能
比不做更糟。

正确的形状已经有先例：ADR-0019 的插件安装用 `.incoming/<rand>` staging 目录——CLI 先把包
复制进去，再经 RPC 指挥发布。发信附件应当照抄这个形状（一个 daemon 拥有的 outbox 目录、
路径与属主硬校验、大小上限、失败清理），但那是独立切片的工作量。

### 9. `APPEND` 到已发送是队列里的一条 op

SMTP 投递成功是**既成事实**。如果 `APPEND` 失败导致 `send` 返回错误，用户会以为没发出去
然后重发——这是最坏的结果。

所以：投递成功后入队一条 `append` op（ADR-0027 的队列），`send` 立刻返回成功。归档失败
可重试、在 `listPendingOps` 里可见。`APPEND` **不可重放**（重放会在已发送里留下两份），
因此和 `move` 一样，「结果未知」是终态、交用户裁决。

账户没有 `role = sent` 的文件夹时不入队——没有归档目标，静默跳过并在应答里说明。

schema v5 → v6：`pending_ops.kind` 的 `CHECK` 增加 `'append'`。SQLite 不能修改 `CHECK`，
所以走标准的表重建（新建 → 拷贝 → 删除 → 改名），在同一个迁移事务内完成。

### 10. 委托 provider 的发信合同不变

ADR-0021 的 `transport/send` 是纯文本单收件人合同。本片**不扩展它**：委托方向的账户继续
只能发纯文本。理由是合同扩展要求所有已发布 provider 同步升级，而收益（给一个第三方
邮件 API 加 Cc）远小于代价。委托账户的 Cc/Bcc/HTML 在 API 层被明确拒绝，而不是静默丢弃。

## 备选方案与取舍

| 方案 | 为何不选 |
|---|---|
| MIME 组装交给前端 | 换前端就会换掉 `References` 的正确性；三个前端三种错 |
| Bcc 写进头部再让服务器剥离 | 服务器不保证剥离；泄露密送名单是不可逆的 |
| 用 `lettre` 等邮件构造库 | 会带进整套 SMTP 客户端与异步运行时假设，而我们只要 MIME 组装这一小块；现有 transport 已经跑通并被真实服务商验证过 |
| 外发 `Date` 头附本机时区偏移，或为格式化额外引入日期库 | 外发报文头暴露发件人本地偏移会泄露物理时区隐私，且破坏 Sent `APPEND` / 持久队列载荷的确定性；UTC `Date:` 用 30 行 civil-from-days 即可测，本机回复引用则直接走 POSIX `localtime_r` 输出显式 `（UTC±HH:MM）` |
| 正文用 quoted-printable | 对中文膨胀 3 倍，唯一优势只在混合内容里成立；多一个编码器多一处出错 |
| 让服务器生成 `Message-ID` | 本地不知道它，`APPEND` 的副本与投递出去的那封对不上，会话链断 |
| `APPEND` 失败就让 `send` 报错 | 用户会以为没发出去然后重发——最坏的结果 |
| 同步 `APPEND`（发完立刻归档，失败重试到成功） | 会把一次发信变成一个不确定时长的操作 |
| 附件用 base64 走现有帧 | 700 KiB 上限，任何一张照片都超；用起来就失败 |
| 扩展 `transport/send` 合同支持 Cc/HTML | 要求所有已发布 provider 同步升级，收益远小于代价 |
| 主题超长时截断 `References` 的尾部 | 会话根在首条；丢首条会让整条会话断开，比丢中间几条严重得多 |

## 后果

- 发出去的信从此带 `Date` 与我们自己的 `Message-ID`，本地能把它和会话对上。
- 中文主题会以 `=?UTF-8?B?...?=` 出现在原始报文里——这是正确的，但用 `grep` 看原文的人
  需要知道。
- 已发送里的副本是**我们组装的那一份**，不是服务器可能改写过的版本。两者的差异（例如
  服务商追加的 `Received` 头）是预期的。
- 归档到已发送最长晚一个 sweep 周期出现在列表里（ADR-0026 决策 3）。
- 委托 provider 账户不支持 Cc/Bcc/HTML，调用时明确报错而不是静默降级。
- 回滚到 v6 之前的二进制无法打开已升级的库；已入队的 `append` op 会被旧版本的 `CHECK` 拒绝，
  这正是 fail-closed 的用意。

## 验证

`crates/maild/tests/` 覆盖：

- v5 → v6 迁移（`pending_ops` 表重建后既有 op 保留）与 v1–v5 备份恢复路径；
- RFC 5322 日期格式、闰年与世纪边界；`Message-ID` 的形状与唯一性；
- RFC 2047：纯 ASCII 不编码、中文编码后可被 `mailparse` 解回原文、长主题折行不切碎字符；
- 正文编码选择：ASCII 走 `7bit`、非 ASCII 走 `base64`，两者都能被 `mailparse` 解回原文；
- MIME 结构：纯文本 / text+html alternative / 带附件 mixed 三种形态可被 `mailparse` 解析，
  且附件字节与原件逐字节相同；
- **Bcc 不出现在任何头里，但出现在信封收件人集合里**；头注入尝试被逐项校验挡下；
- 主题归一（多层 `Re:` 只留一个、中英文前缀）、`References` 继承与超限时保留首条；
- 全部回复排除账户自身地址与其别名；转发携带原附件；
- 投递成功后入队 `append` op；没有已发送文件夹时不入队；`APPEND` 的「结果未知」是终态；
- 假服务器 e2e：多收件人信封、Sent 归档后可在该文件夹读到、委托账户拒绝 Cc/HTML。
