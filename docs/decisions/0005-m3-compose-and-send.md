# ADR-0005：M3 写信使用内存草稿与单次发送状态机

- 状态：Accepted
- 日期：2026-08-20
- 适用范围：M3 桌面写信体验

## 背景

JSON-RPC v1 已提供纯文本 `send`，但桌面层仍需要把字段校验、异步结果、重复提交和草稿
离开行为变成明确的用户状态。SMTP 请求的结果存在不确定窗口，界面不能因为按钮连点产生
多个事务，也不能在失败后丢掉用户刚写的内容。

现有账户 DTO 只公开账户名和连接状态，不公开可安全推断的发件地址。SMTP transport 也是
全局服务，因此桌面端不能把账户名或认证用户名冒充为 From 地址。

## 决策

- 写信作为现有单窗口工作台中的专注编辑区，不新增独立窗口。From 和 To 都由用户输入，
  当前各支持一个 ASCII addr-spec；主题和正文保持纯文本；
- `maild-client` 暴露与服务端一致的字段上限和校验函数，`RpcClient::send` 与
  `ConnectionHandle::send` 在进入网络前再次校验。服务端仍是最终权威边界；
- 桌面正文输入限制为 64 KiB，低于协议的 512 KiB 上限。这样 stock egui `TextEdit` 不会
  因超大粘贴而持续布局数十万字符；脚本和 CLI 仍可使用完整协议上限；
- 输入缓冲在插入时按 UTF-8 字节边界截断，不先保留超限字符串。字段错误在提交后就地显示；
- 每个编辑器最多只有一个活动发送 generation。发送期间字段和按钮全部禁用，旧结果不能
  清除新一轮内容；
- 失败时保留 From、To、主题和正文，只把有界诊断写入状态；成功后立即清空所有编辑内容，
  再显示单一成功结果；
- 返回收件箱或关闭窗口遇到脏草稿时显示确认。发送尚未确认时不能返回收件箱；窗口退出需
  再次明确确认。根窗口关闭通过 `ViewportCommand::CancelClose` 拦截，再由确认结果发起关闭；
- `⌘/Ctrl+Enter` 发送，Escape 请求返回收件箱。所有网络工作继续由独立 Tokio runtime 和
  `ConnectionHandle` 执行，egui 绘制阶段不阻塞。

草稿只存在于当前桌面进程内。持久草稿、多个收件人、附件、HTML、回复和转发都需要新的
守护进程能力，不在本决策内。

## 后果

- 桌面端从不读取 SMTP 用户名、密码或 bearer token，也不会把凭据写入 ViewState、错误卡片
  或成功页；From 地址是邮件内容，不是认证凭据。
- SMTP 已接受但响应尚未返回时，界面明确呈现未知结果窗口并阻止第二次提交。
- 进程崩溃或强制退出仍会丢失内存草稿，这是 v1 明确限制，不伪装为已保存。

## 验证

- shared client 测试覆盖地址、控制字符、NUL 和字段字节上限；
- compose reducer 测试覆盖重复提交、失败保留、成功清空、过期结果、离开确认和 UTF-8
  有界输入；
- 420/800/1280 三档无窗口绘制覆盖长正文和快捷键；
- macOS 实际窗口通过回环 HTTP 接入临时 maild 和假 SMTP，验证内联错误、草稿返回确认、
  成功投递与清空、连接拒绝后内容保留，以及延迟响应期间控件禁用。
