# 前端扩展设计：默认界面也是插件宿主

状态：**评审稿 v1.1**。2026-09-11。用户已认可主界面总体方向，并补充要求：插件能够在默认前端内增加功能、视图，甚至扩展窗口。本文落实这条设计要求，具体 SDK/manifest/权限协议仍需实施前 ADR，不宣称现有 v1 已支持。

## 1. 产品结构

默认 Tauri 前端负责装配界面。功能模块通过稳定扩展点注册自己的命令、视图、设置与窗口。安装一个插件后，用户可以直接在熟悉的邮件界面使用它，也可以把它的视图移到独立窗口。

三类能力可以由同一个安装包共同提供：

| 能力 | 作用 | 例子 |
|---|---|---|
| 内核插件 / provider | 收发、规则、后台任务、数据服务 | NodeSeek Email |
| 完整前端插件 | 提供整个应用界面，可设为默认 | Maild UI、第三方 TUI/GUI |
| **界面扩展** | 向支持的前端贡献命令、局部面板、工作页和窗口 | 邮件摘录、附件工具、联系人资料 |

同一插件可以只有声明式 UI，也可以同时有独立的后台服务。使用 UI 扩展不要求用户更换默认前端，也不要求每个简单按钮启动一条后台进程。

### 默认功能如何做到插件化

窗口、布局、注册表、命令路由、权限检查与修复启动器构成小型宿主。收件箱、阅读器、写信、搜索、账户中心等按用户可理解的功能模块装配；模块使用相同的命令/视图/设置注册与 dispose 生命周期。

随包模块不绕过注册表直接往全局 DOM 塞入口。第三方扩展也不修改宿主私有 DOM/CSS 或动态导入任意 React 组件。可信、随包编译的模块与外部不可信内容有不同的执行隔离方式，但共享贡献点语义；不能把“相同接口”写成“相同信任级别”。

默认安装保证普通邮箱功能齐全。用户可以替换整个前端；单独替换“阅读器”等核心角色时，须先验证兼容提供者再切换。不能在没有替代者时停用仍被使用的必需角色。其余可选扩展可独立开关。

## 2. 界面扩展点

以下命名是拟议 SDK 标识，**尚非现有 manifest 字段**。

| 扩展点 | 可贡献内容 | 布局与交互规则 |
|---|---|---|
| `commands` | 有名称/来源/条件/快捷键的动作 | 统一命令入口，默认不占常驻工具栏 |
| `message.actions` / `message.contextMenu` | 单封/多封邮件动作 | 放“扩展操作”组；可固定常用项，数量有界 |
| `message.badges` | 文本/图标状态，如已摘录 | 由宿主绘制，最多显示 2 个，其余展开；不能改主题/发件人 |
| `reader.sidePanel` | 与当前邮件相关的完整面板 | 默认收起，打开后显示来源和绑定的邮件；窄屏使用阅读区内切换 |
| `workspace.views` | 独立工作页，如摘录集、附件清单 | 侧栏“扩展”组；按需打开，不替换收件箱默认入口 |
| `workspace.bottomPanel` | 批处理进度、导出结果等任务视图 | 不劫持阅读滚动，默认关闭；失败能保留记录 |
| `compose.actions` / `compose.assistPanel` | 模板、签名选择、附件辅助 | 插件先给建议/预览，改收件人或正文需明确操作；不得隐式发信 |
| `account.settings` / `settings.sections` | 插件自己的配置 | 账户提供方与 UI 模块可分别注册；秘密字段由宿主凭据表单处理 |
| `status.items` | 小型后台状态与任务提示 | 合并在活动入口，不让每个插件常驻闪烁/弹 toast |
| `window.views` | 可分离的完整插件视图 | 用户主动打开；有固定宿主标题栏、来源、关闭与收回动作 |

声明式贡献优先：按钮、菜单、徽标、标准表单由宿主统一绘制，避免每个插件重复安装 UI 框架。复杂视图使用插件自己的 Web UI，运行在受限的隔离上下文。

这些是可注册的位置，不是默认全部显示的空插槽。**没有启用可选扩展时，当前三栏界面保持原样。** 新安装扩展先出现在扩展管理页和命令入口；侧栏/工具栏常驻入口由用户固定，或通过一次明确的启用流程展示。

## 3. 同窗口与独立窗口

“扩展窗口”覆盖三种明确的产品行为：

1. **同窗口面板**：一边读邮件一边看摘录、联系记录或处理结果。
2. **工作区页面**：插件需要更多空间时打开自己的工作页；“返回邮件”保留原阅读位置。
3. **独立 OS 窗口**：用户点“在独立窗口打开”，视图可放到另一块屏幕；也能“收回主窗口”。

阅读邮件仍默认原位打开。独立窗口是插件工作流的选择，不把正常 HTML 阅读改回每封信弹窗。

### 窗口所有权

所有扩展窗口由默认前端的 Window Manager 创建和拥有，插件请求一个已注册 view，而不是执行任意系统命令。窗口显示 `视图名 · 插件名 · Maild`；标题栏/权限提示属于可信宿主，插件不能隐藏来源或冒充系统授权弹窗。

每个 `(pluginId, viewId, contextSession)` 默认只有一个可编辑实例。重复打开聚焦已有窗口；分离后原面板显示“已在独立窗口打开”占位，不能同时保留两份互相覆盖的编辑器。收回时先完成状态交接，再关闭原容器；交接失败保留原窗口，避免两边都空。

候选窗口预算：同一插件最多 2 个、全宿主最多 4 个独立扩展窗口；超过时引导切换/关闭已有窗口。具体默认数随真机使用验证，SDK 始终要求有界。窗口位置/大小只保存非敏感布局；邮件标识与内容不放 URL、窗口 label 或系统标题。

### 焦点、退出与独立后台

- 主窗口最小化不强行隐藏用户已分离的扩展窗口。
- 关闭主窗口但仍有扩展窗口时，UI 进程保持运行；最后一个 UI 窗口关闭后释放 UI 进程资源，maild 后台继续按配置运行。
- “退出 Maild 界面”关闭所有前端窗口，先保存各视图未完成内容；它与“停止后台收信”分开。
- 扩展窗口自身关闭时，保存成功后释放实例；失败明确保留窗口或提供放弃，不能无限等待插件回调。
- 界面关闭不暗示停止独立 provider。后台功能仍遵循 package 的 supervised/independent 生命周期和用户启用状态。
- 插件更新/停用会撤销其所有入口、通道和窗口；有未保存内容先做有界收尾。插件卡死时宿主提供强制关闭及内容恢复说明，不冻结其他邮件操作。

## 4. 交互示例：邮件摘录

原型顶部新增“扩展示例”。这是一个虚构的 UI 插件，用于证明扩展位置与生命周期，不是新增真实笔记产品。

1. 打开示例，阅读工具栏出现“摘录”，侧栏出现“摘录集”。
2. 点击“摘录”，阅读区右侧出现面板，固定显示插件来源和当前绑定邮件。
3. 初次只显示“尚未获准读取这封邮件”。用户点“允许读取这封邮件”后才展示该样本的摘要。
4. 输入自己的摘录。切换邮件不会悄悄改变这个面板的绑定；有明确“切换到当前邮件”动作。
5. 点“在独立窗口打开”，视图迁出，原位置显示“聚焦窗口 / 收回主窗口”。
6. 独立窗口可编辑；收回后保留文本。浏览器阻止弹窗时保留原面板并说明开启方式。
7. 设置 → 扩展可以停用示例；按钮、侧栏入口、面板和扩展窗口一起退出，本次演示内容仍可在重新启用后恢复。

示例脚本是可信设计资产，同一个 HTML 中模拟注册/隔离/状态交接，**不具备生产插件沙箱与权限保证**。允许按钮仅模拟 UI 同意，不访问真实邮箱。

## 5. 模块和数据流

```text
                        maild daemon
                 邮件数据 / 授权 / 插件服务
                             ^
                             | 有身份、有范围的调用
                             v
                Tauri Rust bridge / request broker
                  ^                  ^
                  | 用户操作         | 扩展请求（保留插件身份）
                  v                  v
  默认前端宿主：注册表 + 命令 + 布局 + 窗口 + 权限门禁
       |                    |                    |
       v                    v                    v
  随包功能模块          外部扩展隔离视图        邮件 HTML 文档
  可信、编译期装配      JS 按需启用，受限桥接    禁 JS，无应用桥接
```

插件 UI 的脚本可以运行，用来实现交互；邮件 HTML 的脚本仍然禁止。两者不能复用同一个带权限的渲染上下文。一个邮件中的 `postMessage` 不能被当作插件命令。

宿主处理请求时使用**插件身份、视图会话、账户/邮件授权范围、操作白名单的交集**，不能把任意消息转发为受信前端的 user 请求。用户给默认前端的账户管理能力，不会自动继承给它承载的 UI 插件。

允许“在窗口显示”与允许“读取全部邮件”“访问网络”“修改草稿”“执行邮件操作”是不同授权。仅注册按钮无需读取邮件正文；可见性条件只能使用必要的非秘密布尔上下文，例如是否选中邮件，而不是推送全量对象供插件自行判断。

## 6. 原文与扩展数据的边界

插件可以返回摘要、翻译、标注或建议，呈现在自己的面板；不就地改写存储的原邮件或把结果覆盖成发件人正文。将来做正文内高亮，也需要专门的声明式装饰接口，不开放任意脚本注入。

同意读取某封邮件后，用户必须能看见对象范围。上下文默认固定，跟随选中邮件属于独立开关和授权；切信、切账户、换会话 generation 会让旧回执失效，插件结果不能误显示到下一封信。

UI-only 扩展默认无网络、无任意文件访问、无系统命令权限；需要云处理时，在首次使用前说明会向哪个服务发送哪些数据。允许联网的域名与读取邮件的范围分开确认。

**现有 native executable 插件仍属于当前用户信任域**，能够直接使用系统网络/文件 API。本文的 UI 沙箱和受限桥接不把现有原生插件变成安全沙箱，不能宣称宿主的开关能限制一个同用户恶意进程。安装页需区分纯 UI 内容与包含原生代码的包。

## 7. 契约范围

实施前为 `ui-contributions` 制定独立 schema 与 API 版本，作为受管 package 的可选 UI 描述部分：已有 provider 包可增加 UI 部分，纯 UI 包不必伪造后台 executable。具体文件名和 envelope 归新 ADR；**不能往 v1 manifest 塞未定义字段并宣称兼容**。

最小描述包含：插件身份/版本、宿主 API 范围、贡献列表、类型与稳定 ID、资源入口、主题/语言资源、激活条件、请求能力、状态版本和清理策略。ID 以插件命名空间隔离；排序相同用稳定 ID 打破平局。条件语法是受限声明，不能 eval 插件字符串。

注册、启用、激活、隐藏、分离、回收、停用是可观察状态。注册返回可销毁句柄；卸载时移除命令、事件监听、计时器、视图和窗口。升级先校验新贡献与 API 兼容性，再整体切换；重复/无效贡献只隔离对应插件，不能使收件箱无法启动。

完整前端可声明支持哪些 UI 扩展点和 API 版本。换成不支持某视图的第三方前端时，后台 provider 继续运行，扩展管理显示“当前前端不支持此界面”；不假定每个 TUI 都能运行 Web UI。

## 8. 实现边界与资源预算

Tauri 提供窗口/WebView 级 capability，但多份 capability 命中同一个窗口会合并权限；动态扩展窗口不能继承 `windows = ["*"]` 的宽泛授权。[Tauri capability 文档](https://v2.tauri.app/security/capabilities/)

应用自定义 commands 的暴露还需单独收紧，不能仅靠给窗口分配名字。schema 小、类型安全的 broker 命令是扩展 UI 的唯一入口；不开放任意 RPC、文件路径或系统窗口操作直通。[Tauri 自定义命令范围](https://v2.tauri.app/security/capabilities/)

复杂 UI 只在可见/激活时创建。隐藏默认保存小型状态并销毁/挂起，不为每个已安装插件常驻一个 WebView；是否保持活跃需显式理由和预算。VS Code 的文档也明确持续保留隐藏 WebView 有额外内存成本，建议优先保存/恢复状态。[Webview 状态与持久化](https://code.visualstudio.com/api/extension-guides/webview#persistence)

持久数据放宿主提供的插件命名空间存储或已授权的插件数据域，UI 不自行开一个未经治理的 localStorage 邮件副本。状态跨版本恢复失败只影响扩展；宿主能丢弃布局缓存重新打开，不能碰邮件库。

## 9. 实施切片

| 切片 | 时点 | 可独立交付内容 | 验收 |
|---|---|---|---|
| E01 贡献注册底座 | **03 骨架内，从第一天采用** | command/view/settings registry、稳定 ID、dispose、默认模块装配、声明式 mock 扩展 | 同一个示例命令可出现在菜单/工具栏；停用无遗留；重复 ID/版本拒绝不阻塞邮箱 |
| E02 外部界面运行与授权 | G01 后，04/08 前对齐边界 | package UI 描述、隔离视图、受限 bridge、插件身份/范围、设置与来源 UI | 假冒来源、越权读下一封、脚本邮件伪装插件、禁用后旧通道重放均拒绝 |
| E03 视图与窗口管理 | 08 中，10 前完成 | reader 面板、工作页、detach/reattach、单编辑实例、dirty/退出/升级矩阵 | 真窗口多次打开不重复；分离/收回不丢内容；插件崩溃只影响其视图 |

实现顺序为：设计确认 → G01 与扩展契约 ADR → 03 + E01 → E02/04 → 08 + E03 → 09/10。先用最小“摘录”测试插件验证整个界面生命周期；不把翻译、看板等业务插件列为当前交付前置。

最小可交付路线是 E01：默认功能都经注册底座装配，未来外部加载不需重写壳。用户要的完整第三方界面与独立窗口能力依赖 E02/E03，不能把“预留了接口”汇报成完整插件扩展已经可用。

暂估新增 E01 2–4、E02 3–5、E03 2–3 人日，共 7–12 人日；在原待确认日用范围 29–43 基础上，全范围约 **36–55 人日**。这是范围评估，非时间承诺；原生窗口/身份授权 ADR 明确后再校准。

## 10. 验收补充

- 零可选扩展、一个扩展、十个贡献拥挤时，原界面仍可读，用户能固定/隐藏入口。
- 纯声明式 UI 无独立 WebView；首次点复杂视图才创建；隐藏后内存和监听按契约收回。
- 1440px 侧栏面板并排；1024/768/375px 占阅读区单层，返回邮件动作始终可见。
- 相同 view 多次打开、快速分离/收回、关闭主窗口/最后扩展窗口、升级/停用/崩溃有确定结果。
- 主题、缩放、中文长名、键盘和读屏继承宿主基线；扩展来源不能被自定义 CSS 隐藏。
- 插件改草稿后 generation 不一致必须重确认；看信不自动向插件发送正文；上下文权限失效立即断开。
- 正文脚本禁用与插件脚本允许在独立测试中验证；Tauri capabilities、command allowlist 和 daemon principal 三层分开验收。

## 参考

仅借鉴扩展模型，没有复制实现：

- [VS Code Contribution Points](https://code.visualstudio.com/api/references/contribution-points)：声明式菜单、命令、设置与视图。

关键取舍：稳定贡献点与受管视图有维护成本，但能保住可替换性、统一交互与资源预算；任意 DOM 注入会使宿主升级与主题重构直接破坏插件，当前不采用。


### 08-B 内置贡献补充（ADR-0037）

邮箱模块新增搜索/同步活动导航、标记/归档/移动/删除命令与 activity 核心工作页，仍经相同注册表。
受限条件增加 `online-message-selected`（后台在线且已选邮件），用于需要写入的命令；原
`message-selected` 继续允许离线的只读扩展动作。条件只读宿主布尔上下文，不扩大插件数据权限。
外部隔离 UI 和独立窗口仍由 E02/E03 交付，本片不把内置 React 模块当作第三方执行沙箱。

### 08-C 设置贡献补充（ADR-0038）

账户、通知与规则、地址、扩展和后台设置继续经 E01 settings 贡献注册，与邮箱提供的阅读隐私并列。
界面模块开关与 daemon 受管包启停分别显示，避免把隐藏工作页误认为停止收信服务。
宿主增加导航确认缝，设置未保存时确认离开；通知等待批准后才切页并定位，关窗批准后到草稿
保存完成期间锁定设置。外部 UI 尚不能注册任意 React 组件或借用这些管理命令。
包管理权限仍为 ADR-0030 的受托前端权限；来源、版本和授权在安装及回滚前明确展示。
